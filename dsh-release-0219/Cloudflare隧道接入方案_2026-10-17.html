🛰️ Cloudflare 隧道接入方案

dsh-companion（Kotlin） + dsh-remote-bridge（TS） · 适配 UOS 20 · 2026-10-17

一句话结论：bridge 本身用 Node 原生 http 监听 + ws 升级，不做 TLS 终止；客户端 OkHttp 原生支持 https/wss。所以 Cloudflare 隧道 = cloudflared 进程在你电脑上把主机的 HTTP/3090 反向代理到 Cloudflare 边缘，由 Cloudflare 提供 wss:// 与固定域名，两端代码几乎零改动，核心工作量集中在「设置面板自动创建隧道 + 国内源下载 cloudflared + 生成 wss 配置文本」。

1. 现状与能力盘点（已核对源码）

层现状（代码实证）对 Cloudflare 隧道的影响
server.ts 监听node:http createServer，upgrade 交给 WebSocketServer；默认绑 0.0.0.0:3090，仅存 loopback 时也处理无需改 bcloudflared 回连 localhost:3090 即可，隧道不用开「绑定外网 IP」
TLS 终止bridge 不做 HTTPS，wss:// 的「s」由反向代理承担符合 Cloudflare 边缘统一终止 TLS，回源走本地 http
REST/WS 基址REST /api/v1，WS /events（DshClient.kt eventsUrl() = base.newBuilder().addPathSegment("events")）透明 隧道只换主机头，路径原样穿透
客户端认证Authorization: Bearer 设备 token；回环已设备换warn 隧道暴露公网，App 端 token 放头部透传 不受 CF 校验，仍由 bridge 鉴权，可接受
断线重连ReconnectingEvents 指数退避 1→30s，closed 才停warn Quick Channel 地址漂移后仍死连旧地址，需处理（见 §5）
配置文本config-text.ts 生成 DSH1: 多端点（LAN/VIRTUAL_NET/WAN），ConnectionShare.kt 解析复用 加一个 WAN 类端点 wss://xxx.trycloudflare.com 即可，两端数据模型已支持
App 下载二维码app-qr.ts APP_QR_CODES 内联 SVG，指向 GitHub/Gitee Releases 列表页复用 Gitee 即国网较快入口

2. 两种 Channel 对比与选型

✦ Cloudflare Channel（命名 Tunnel）⚡ Quick Channel（Quick Tunnel）
是否需要账户/域名需要 Cloudflare 账户 + 自己域名 + DNS（CNAME→<tunnel-id>.cfargotunnel.com）无需
对外地址固定：wss://your.domain.com临时：wss://<random>.trycloudflare.com（每次重建变）
稳定性⭐ 好，域名固定，适合长期使用隧道进程重启地址变，连接需刷新
国内直连Cloudflare 边缘，国内时好时坏（受运营商影响）同左
适用场景有域名的人长期远程回家临时演示、测试、无常人域名兜底
UOS 20 落地都用同一个 cloudflared CLI，只是参数不同；架构完全共享
推荐策略：设置页两个按钮——「创建命名隧道（稳定）」「创建快速隧道（临时）」。无账户时先 Quick 体验，有域名再切 Named，两种模式共用一套「隧道状态 → wss 地址 → 配置文本」管线。

3. 整体架构

✦ 命名隧道（固定域名）

📱 Appwss:// Cloudflare 边缘TLS 终止 🏠 电脑 cloudflaredlocalhost:3090 dsh-remote-bridge

DNS: domain → cfargotunnel.com；隧道凭证 tunnel.json + cert.pem

⚡ 快速隧道（临时）

📱 Appwss://xxx.trycloudflare.com Cloudflare 边缘TLS 终止 🏠 电脑 cloudflaredlocalhost:3090 dsh-remote-bridge

无需凭证，一条命令即起；地址每次不同

回源为何走 localhost 而非 0.0.0.0

bridge 默认绑 0.0.0.0:3090 会对外网暴露监听口。走隧道时不必那样——cloudflared 与 bridge 同机，回源指 127.0.0.1:3090 即可，局域网仍走原本的 LAN 端点。安全上隧道只暴露一个「CF 到本机」的链路，比裸开 0.0.0.0 干净。

4. 改造点拆解（两端落地）

4.1 服务端 bridge（TypeScript）

  • settings-adapter.ts / src/client/workspace.tsx：在「远程访问」卡片下新增「Cloudflare 隧道」分区，两个按钮（命名/快速）+ 状态区 + 生成的 wss:// 配置文本一键复制。
  • config-text.ts：新增 endpoints 组装——把隧道 wss://… 归一为 https://… 作为 WAN 类端点插入（关键：客户端端点必须 http(s):// 前缀，不能直接给 wss://，见 §5），并自动排序在 LAN 之后。Kotlin 侧 EndpointKind 自动推断为 WAN。
  • 新增 src/host/cloudflared.ts：封装 spawn cloudflared 子进程（Quick 解析 stdout 的 trycloudflare.com URL；Named 指定 --name + 凭证），管理生命周期与「隧道健康探活」。健康探活可复用现有 GET /healthz。

4.2 客户端 companion（Kotlin，改动最小）

  • DshClient.kt：现有 normalizeEndpoint 已接受 https://，HttpUrl 自动把 https→wss 拼 /events。无需改 WS 层，wss 直接可用。
  • ConnectionShare.kt：解码侧无改动，天然吃 wss 地址字符串。
  • ConnectScreen.kt：展示时把 WAN 端点标“☁️ Cloudflare（公网）”标签，已是 WAN 分类可复用。
唯一实质新增在服务端：生成 wss 端点要归一成 https:// base，正是 §5 的坑。

5. 关键坑位（务必读 PITFALLS 再动手）

6. 设置页自动逻辑 + 国内源下载（核心卖点）

UOS 20 / x86_64 的 cloudflared 适配

项值 / 做法
校验安装环境先装 cloudflared。安装前 getconf LONG_BIT 确认 x86_64 → 下载 amd64 归档（UOS arm64 设备别拿错）。首次 spawn 用 500ms 探活 --version 兜底
国内优先源探测顺序：先测 install.appfoster.com / registry.npmmirror.com 类国内可达性（或读已有 `注册表` 镜像），失败回退 GitHub 官方 github.com/cloudflare/cloudflared/releases
UOS 9 生态位UOS 20 (Eagle) apt 源省内不一定有 cloudflared 包，故走「官方二进制 + 解压到 ~/.local/share/dsh-cloudflared/」最稳，不碰 /usr 权限
① 检测系统的架构/网络→ ② 择国内源下载 cloudflared→ ③ 失败↓回退 GitHub / 手动路径→ ④ 创建 Quick/Named 隧道→ ⑤ 生成 wss 配置文本 + 复制 
// 设置页「Cloudflare 隧道」自动创建流程（伪码）
async createTunnel(mode) {
  const exe = ensureCloudflared()            // 国内源优先下载，ams&镜像回退
  if (mode === 'named')
    await loginAndCreate(showAbort)          // 需账户；可让用户填 token 或走交互
  const url = await spawnTunnel(exe, mode)   // Quick 解析 trycloudflare.com，Named 读 ssl
  const cfg = await buildDsh1Config(url, scheme='https')  // 归一化
  copyToClipboard(cfg); renderStatus(url)     // 展示 wss:// 并一键复制
}

7. 边界与后续建议

  • 安全：隧道只在「远程访问」已启用时才会生成；App 令牌仍由 bridge 鉴权。建议面板给「生成后立即吊销/关闭」入口。
  • 国内源：cloudflared 下载与 App APK 都走 Gitee / npmmirror 镜像，标注「国内网络优先」。
  • 后续增强：Quick 地址漂移时，App 可加「切换 WAN 端点并重连」让体验接近“自动更新”而非手动贴新码；Named 通道可在 cloudflared 守护自拉起（systemd 或单例 double-fork）。
  • 真机验收：涉及内核交互与公网链路，务必像既往 DSH 调试链路一样：先本地起 Quick 隧道、手机用 wss 地址连一次真机，再谈发布。
