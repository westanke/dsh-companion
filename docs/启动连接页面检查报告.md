## 二、问题 1：右上角按钮点不到

### 2.1 原结构 —— 按钮与滚动层同层交叠

```kotlin
Box(Modifier.fillMaxSize()) {
    Row(modifier = Modifier.align(Alignment.TopEnd).padding(12.dp)) { /* 诊断 + 语言 */ }
    Column(Modifier.fillMaxSize().verticalScroll(…)) { /* 全部内容 */ }
}
```

`Box` 中子项按声明顺序绘制，后声明的 Column **整块覆盖**在按钮之上，而按钮位置恰是 Column 的内容区。

### 2.2 真机现象（修复前）

- `uiautomator dump` 的 39 个节点里，右上角**没有任何节点**对应这两个按钮。
- 网格扫描 x∈{780,828,900,972,1010} × y∈{40,60,80,100,120,150,200} 共 35 点，
  `diag_log` **始终 false**，界面无任何变化。
- 对照组：同屏 Column 内的删除按钮一点就弹对话框 —— 证明 `input tap` 通道正常。

### 2.3 修法 —— 把按钮搬出滚动层

```kotlin
Column(Modifier.fillMaxSize().imePadding()) {
    Row(Modifier.fillMaxWidth().padding(horizontal = 8.dp, vertical = 4.dp),
        horizontalArrangement = Arrangement.End) { /* 诊断 + 语言 */ }
    Column(Modifier.fillMaxWidth().weight(1f).verticalScroll(…)) { /* 全部内容 */ }
}
```

上下分家，命中区零交叠。改动：`ui/ConnectScreen.kt:148-181`。

### 2.4 真机验证（第一轮，通过）

| 动作 | 结果 |
|------|------|
| tap 诊断按钮 | `diag_log` false→true，左上角出现浮层，图标空心→实心，`diag.log` 正常写入 |
| tap 语言按钮 | 中→英→中双向切换，503 个文案键零缺失 |

## 三、问题 2/3/5：断网仍显示「已连接」

### 3.1 根因：状态位记的是历史，不是现状

`HarnessState.connected` **只在两处置 true**（`connectHostInternal`、`loadSnapshot`），
全仓**没有任何代码把它置回 false**。它的真实语义是「曾经连上过」。

三处代码都当成了「此刻还连着」：

| 位置 | 错误假设的后果 |
|---|---|
| 卡片的 `isActive` | 断网了还点亮「已连接」 |
| 按钮点击短路 | 不重连，又被门闩放行/弹回 → 「点了没反应」 |
| 回前台复核判据 | 若沿用它，复核永远不跑 |

### 3.2 真机复现

用 `cmd wifi set-wifi-enabled disabled`（`svc wifi` 在这台机上用法不同）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 断网后冷启动 | 两地址「不可达」+ 诊断面板（本来就对） | 同左 |
| **连着时断网再回前台** | 仍显示「已连接」+「进入应用」 | **自动纠正为未连接状态** ✅ |

### 3.3 修法（方案 B）

新增 `data/ConnectionLiveness.kt`，把三条判据抽成**带名字的纯函数**（都有单测）：

```kotlin
shouldRecheckActiveConnection(connectGatePassed, connected, hasActiveConnection, connecting)
shouldReconnectOnTap(hostId, activeHostId, hasActiveConnection)   // 判据是「客户端还在不在」
hostCardState(hostId, activeHostId, connected)                    // CONNECTED / DISCONNECTED / IDLE
```

配套：

- `MainActivity.onResume` → `recheckConnectionIfOnConnectScreen()`：连接页可见时对当前链路探一次
  `healthz`，失败则 `connected=false` 并清掉失效的 `active`。
  **不走 `launchOperation`**（那个出口会弹 snackbar + 置 busy，每次回前台失败都吵一句红字）。
- 卡片三态分开显示：「已连接」绿点 / 「已断开」红点 / 无状态点（从没连过）。
- 按钮三态三分文案：「进入应用」/「重新连接」/「连接」。

### 3.4 为什么不在 App 内也轮询

进了 App 之后有事件流（`eventsConnected`，断线即 false 并显示「已断开」）盯着链路，
再发健康检查是重复的。连接页是**每台设备的必经入口**，用户回来看的就是「现在通不通」，
一次探活足够。

## 四、问题 4：冷启动后按钮永久变灰（修 #2 时顺手抓到）

### 4.1 现象

断网被复核纠正后，按钮**显示「连接」但是灰的、点不动** —— 而当时没有任何请求在跑。

### 4.2 根因

`connectHostInternal` 里有一行 `busy = true`，而这条函数有两个调用方：

| 调用方 | 谁负责清 busy |
|---|---|
| `connectHost` / `pair` / `importConfiguration` | `launchOperation`，结束时 `copy(busy = false)` |
| `restoreConnection`（冷启动自动重连） | **没有人** —— 直接 `runCatching { connectHostInternal(target) }` |

于是冷启动自动重连成功后 `busy` 永远是 true，连接页所有按钮的 `enabled`
（`!state.busy && !state.connecting`）一律落 false，且只在进程重建时才复位。

### 4.3 修法

`connectHostInternal` 内改为 `busy = false`，注释写明「busy 的所有权归 `launchOperation`」。

**铁律（已进 `PITFALLS.md`）**：`busy` 只该由发起操作的公共出口置位与复位；
被它调用的函数不许自己置 `busy = true` —— 那条路径可能有别的入口进来，没有收尾者。
