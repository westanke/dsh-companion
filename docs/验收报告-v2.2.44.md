## 三、❌ 失败项（3）

### 【F1｜严重】权限档位 Pill 与 ⋯ 菜单权限项完全不渲染

**现象**：发送区上方**没有**常驻权限档位 Pill；顶栏 `⋯` 菜单只有
`轨迹 / 会话统计 / 模型 / 追加引导` 四项，**没有权限切换**。

- 复现：连接 → 任一会话 → 看发送区上方与 ⋯ 菜单
- 多会话验证：第 2 条（测试会话）与第 4 条（真实会话）结果一致，排除会话因素
- 证据：`ui/43-menu3.xml`、`ui/127-menu4.xml`、`shots/80-settings3.png`

**根因（已定位到源码级）**：

App 侧 `data/ChatPresentation.kt:54` 读的是

```kotlin
val raw = values.objectValue("permissions") ?: return null
val currentValue = raw.stringValue("currentValue") ?: return null
val options = (raw["options"] as? JsonArray).orEmpty()...
```

而当前 DSH 的 `permissions` 投影是

```json
{"preset":"danger-full-access","sandbox":"danger-full-access","approval":"never","seeded":false}
```

**没有 `currentValue`，更没有 `options[]`**，于是 `permissionSelect()` 恒返回 `null`；
`ChatPermissionPill.kt` 首行即 `if (permission == null || permission.options.isEmpty()) return` → 整条不渲染。

再往下一层，DSH `dsh-permission-presets` 的 wire 视图本身就是

```js
const selectionSchema = z.object({ currentValue: z.string().min(1) })
// wire.view: (state) => ({ currentValue: this.derive(state) })
```

**预设清单在独立的 `permissionPresets.catalog()` 远程服务里，投影里根本没有 `options`**。
所以即使 bridge 改传 wire 视图，App 仍拿不到候选项。

**影响**：PARITY.md 标记为 `done` 的「会话权限预设」在真机上**完全不可达**。
v2.2.44 新增的 Pill 因此是「永远不渲染」的状态。
用户只能手打 `/permission <预设名>`，而斜杠命令的结果又不回显（见 F3 的同类问题）——等于死路。

**修复方向（二选一）**
1. 在 `dsh-remote-bridge` 增加 `GET /chat/permission-presets`（BFF，透出 `permissionPresets.catalog()`），
   App 改为「投影取 currentValue + 目录接口取 options」；
2. App 侧改为读 `permissions.preset/sandbox` 显示当前档位，候选项先内置
   （`read-only` / `workspace-write` / `danger-full-access`，见 `dsh-bash-sandbox/README.md`），
   后续再接目录接口。

### 【F2｜严重】文件页「创建文件 / 新建文件夹」静默失败

**现象**：创建对话框正常弹出、名称可输入、点「创建」后对话框关闭，
但**文件没有创建、列表不刷新、没有任何错误提示**（snackbar 不出现）。

- 复现：文件 → 根目录 `/` → 创建 → 新建文件 → 填名 → 创建
- 对照组：同样步骤选「新建文件夹」，同样静默失败
- 连测 3 次（e2e-v2244-probe.md / e2e-probe2.md / e2e-probe3.md / e2e-probe-dir），全部失败
- 制造冲突（用 shell 先建同名文件）后 App 内再建，**预期中的 409 冲突错误也没有显示**
- 服务器侧确认：`ls /media/wangke/OFFICE/workspace/e2e-*` 全部不存在
- bridge 审计表确认：`SELECT COUNT(*) FROM audit WHERE action LIKE 'file%'` = **1**（历史遗留），本次**无 `file.create` 记录**
- 证据：`ui/101-create.xml`、`ui/103-newfile2.xml`、`ui/104-after-create.xml`、`shots/103-create-result.png`

**已排除**
- scope 缺失：设置页显示持有「写入文件」scope，而 bridge 的创建端点只要求 `files.write`（`router.ts:968`）
- 代际闸门：`requestGate.isCurrent()` 只挡**状态回写**，不阻止请求发出（`HarnessViewModel.kt:757`）
- `selectedRootId` 为空：同页的列表读取正常，连接快照里 `selectedRootId` 必有值（`HarnessViewModel.kt:664`）

**未定位**：请求为何没有到达 bridge（无 401/403 审计、无文件生成）。
**下一步取证需要**：装 debug 包后 `run-as` 取 token + 桥侧请求日志，或临时给
`launchOperation` 加一条屏上探针打印 `messageOf(throwable)`。

**影响**：文件页的写入类能力（新建、上传、移动、删除）在真机上大概率同样不可用
（它们共用 `withClient`/`launchOperation` 同一模式），**待逐项复测**。

### 【F3｜中】新建会话后 `@` 文件补全永久卡在「正在读取」

**现象**：新建会话 → 在输入区打 `@` → 面板显示
「工作目录文件 / 正在读取会话工作目录…」，**一直不加载也不报错**（等 13 s 以上无变化）。
退出会话再进入（此时列表已刷新）→ 同一会话打 `@` → **正常列出目录条目**。

- 证据对照：`shots/55-mention3.png`（卡死，13 s 后仍是加载态）vs `shots/59-mention6.png`（重进后正常）

**根因**：`HarnessFilesViewModel.kt:144` 的 `loadMentionEntries()` 第一行就是

```kotlin
val session = mutableState.value.sessions.firstOrNull { it.id == sessionId } ?: return@withClient
```

新建会话时该会话**尚未进入 `state.sessions`**（列表是下次进入会话页才刷新的），
于是函数**静默 return**，状态停在 `mentionEntries = null`（= 「还在读」），
既不置 `mentionFailed`，也没有任何重试入口——UI 就永远显示加载中。

**修复方向**：
- 会话创建成功后立刻把它并入 `state.sessions`，再触发 `loadMentionEntries()`；
- 或给 `@` 面板加「重试」/超时兜底，让「读不到」如实显示而不是无限转圈。

## 四、⚠️ 有缺陷但可用（4）

### W1｜会话统计「轮次」口径偏大

真机显示 **轮次 9**，但该会话真实用户轮次只有 **2**。

源码 `data/SessionStats.kt:55` 直接数 `user/message` 事件条数。实测该会话 9 条
`user/message` 里只有 2 条 `source.kind == "user"`，其余 7 条是内核注入
（`runtime-context` ×4、`skill-catalog`、`time-context`、`agent-instructions`）。

**建议**：按 `source.kind == "user"` 过滤。同一问题也会让「助手消息」偏大
（`assistant/message` 每个 step 一条）。

### W2｜Markdown 表格单元格内的行内代码不解析

模型输出的表格里 `` `2026-10-13-07-39-52/` `` **原样显示反引号**。

根因：表格是自绘的（`ui/chat/ChatMarkdownTable.kt`），单元格用 `Text(cell)` 直接渲染，
不做行内 Markdown 解析（`ChatMarkdownTable.kt:176-192`）。表格本体（表头、分隔线、两列布局）本身是对的。

**建议**：单元格值接一次行内解析（行内代码 / 粗体 / 斜体），或至少剥离成对反引号。

### W3｜编辑器无「未保存」保护

在 `PR-app-body.md` 源码视图输入 `ZZTEST` 后：
- 顶栏「保存」按钮**没有任何脏状态指示**（实测高亮/变色/圆点均无变化）
- 直接点「返回」→ **没有任何「未保存改动」提示**，直接退回目录

（本次已手动把改动删回原样，未损坏用户文件。但真实用户改了没保存就返回，改动会静默丢失。）

**建议**：编辑后给保存按钮加脏态；返回时若 dirty 则弹确认。

### W4｜同一个 APK 出现两个构建标识

- 设置页「关于」：`构建 ed91cf3`（git 短哈希）
- 第 4 条会话「本会话的文件」里，Agent 自己写的交付说明提到 `watermark 9863579`

两者不一致。仓库当前 HEAD 是 `ffa9159`，说明真机装的包早于 HEAD。
**「构建水印」功能本身工作正常**（能区分包版本），但水印取值与 Agent 侧产出的 watermark 不同源，
容易在排查「改了没生效」时造成二次困惑。建议统一为一个值。

## 五、⏸ 未验证项（6）
