> 状态：**已实现并真机验证**；未发版（等发话）。

## 一、这次加了什么

### 1.1 三通道诊断日志（`debug/DiagLog.kt`）

为什么是三条通道：`PITFALLS.md` §vivo 实测过**自有 App 的 `Log.i` 在 vivo 真机上抓不到**
（`adb logcat -s DSH_DIAG` 只有 `--------- beginning of main`）。所以任一条通道都不能是唯一。

| 通道 | 落地 | 用途 | 真机实测 |
|---|---|---|---|
| logcat | tag `DSH_DIAG` | 有电脑时最顺手 | ❌ vivo 封（确证） |
| **文件** | `filesDir/diag.log`，128 KB 环形覆盖 | **主力**：`adb` 直接读全文 | ✅ 可用 |
| 屏上浮层 | 内存环形缓冲 200 条 | 人在手机上、没电脑时 | ✅ 可用 |

`release` 包 `BuildConfig.DIAG_LOG=false` → 三通道全静默、浮层不渲染，
**诊断能力不随发布包出厂**。

### 1.2 设置里的滑动开关（用户要求）

`设置 → 操作日志 → 记录窗口与会话操作`（`SwitchRow`），旁边一个「读日志」入口
（整段复制到剪贴板，给没电脑的场景用）。

**连接页右上角另有一个虫子图标**做快捷开关 —— 理由是一条真机教训：
设置页在**连接门闩之后**，连不上服务端时根本进不去，而那恰恰最需要日志。
诊断工具的可用性不该依赖被测功能是否正常。

### 1.3 从文件导入连接码（用户要求）

两条路径，都不经过软键盘：

1. **外部专属目录自动读取**（`getExternalFilesDir()/dsh-connection.txt`）——零权限，
   `adb push` 直接可写，App 启动时自动填入输入框。**无人值守连接走这条。**
2. **SAF「从文件读取」按钮**——给「用户自己从微信/邮箱存下来的文件」用。

### 1.4 插桩点

| 分类 | 打在哪 | 回答什么问题 |
|---|---|---|
| `LIFE` | `MainActivity` 六个生命周期 | 窗口何时被系统回收/重建 |
| `SCREEN` | 亮灭屏广播、`onConfigurationChanged`、`onWindowFocusChanged` | 熄屏断流链路、旋转、分屏 |
| `ROUTE` | `ChatScreen` 的路由分叉点 | **走原生还是 WebView** |
| `COMPOSE` | `ChatDetail` 进入时 | 原生页是否真的在渲染 |
| `SCROLL` | 落底 effect、贴底跟随、`snapshotFlow` | 九版落底逻辑的真实行为 |
| `WEB` | WebView 创建/加载/失败 | 兜底页是否可用 |

### 2.1 核心疑点解答：**走的是原生页**

`#5 ROUTE … useWebChat=false → 原生/ChatDetail` + `#6 COMPOSE ChatDetail 渲染` ——
两条同时出现，确证原生页真的在渲染。

这解开了此前的悬案：上一轮在 `ChatDetail.kt` 里加的 `Log.i` 探针**一条都没打出来**，
当时只能怀疑「改的这个文件不是实际渲染的 composable」。现在答案是：
**文件没错、路径没错，是 vivo 把 logcat 封了。**

### 2.2 落底逻辑正常

`#9 → #15`：等内容 23 拍 → 推 5/10/15 拍（`first` 从 18 → 31 → 42）→
`scrollBy=0`（物理底部），共 18 拍收工。九版改动之后，**当前实现是对的**。

### 2.3 熄屏断流链路正确

另一次实测（含熄屏亮屏）：

```

12:51:28.370 #334 LIFE   onStop
12:51:28.800 #335 SCREEN ACTION_SCREEN_OFF → pauseEvents()
12:51:31.738 #338 LIFE   onStart
12:51:31.741 #339 LIFE   onResume 恢复时 px=1080x2316 dp=360x772 密度=480 方向=竖屏
12:51:32.017 #340 SCREEN ACTION_SCREEN_ON → resumeEvents()
```

顺序与既定策略一致：**熄屏即断流、亮屏即接回**。顺带量到一个事实：
`onStop` 比 `ACTION_SCREEN_OFF` 早约 500 ms（系统先停 Activity 再发广播），
所以断流实际由广播触发，而不是靠 Activity 生命周期。

### 2.4 抓到一个新异常（待查）

`#16 totalItemsCount=1` —— 用户滑动一下之后，LazyColumn 自报的条目总数
**从 53 掉到 1，再回到 53**。

一次滑动不该让列表重建。可疑方向：
- 滑动触发了 `loadOlderHistory`，history 被整份替换（`#17` 又回到 53 支持这个猜测）；
- 或 `snapshotFlow` 在 `isScrollInProgress` 期间读到中间态。

**这条不是「日志功能的问题」，而是日志第一次真机跑就抓出来的真实信号** ——
正是加它的目的。已记入 `STATUS.md` 待查。

## 三、过程中修掉的五个真实缺陷

这五个都是「写完以为对了、真机一跑才发现」的。

### 3.1 `bind()` 与开关耦合 → 文件通道整条死掉

`DiagLog.bind()` 初版写 `if (!enabled) return`。而开关**默认就是关的** →
启动时 `bind` 被跳过 → `logFile` 恒 null → 用户随后拨开开关只改了 `enabled`，
**没人再调 `bind`** → 文件通道永远死着。

现象极隐蔽：**屏上浮层有字、文件里一条没有**（浮层走内存缓冲，不依赖文件）。

修法：`bind` 与开关**彻底解耦** —— 它只记住文件在哪，不判断要不要写。
回归用例：`DiagLogTest` §先关后开时文件通道仍然建立。

> 教训：**「开关」只该管「记不记」，不该管「通道建不建」。**
> 两者混在一起就会出现「先关后开」这种唯一坏序 —— 而它恰是默认序。

### 3.2 日志噪音 344 条 → 17 条

第一版插桩把日志直接写在组合体里，一次进会话刷出 **344 条**，300+ 条是同一句
「ChatDetail 组合」，把 `ROUTE` / `SCROLL` 全淹了。修两处：

1. **打点位置**：会重组的地方改用 `LaunchedEffect(key)`，键取语义上真正会变的值；
2. **底层指数抑制**：`DiagLog` 内与紧邻上一条正文相同时只累加计数，
   且只在 2/4/8/16…（2 的幂）次时落一条「（同前，已重复 N 次）」。

第 2 条放在 `DiagLog` 而不是各调用点 —— 噪音来自**多个**调用点，
逐个加判断必然漏掉下一个新加的。

### 3.3 数字口径混用 → 看着像 bug 其实不是

日志里出现 `displayItems=60 total=57`（前者比后者大），读的人会去查一个不存在的 bug。
实际：`displayItems` 是**分组前**消息项数，`total` 是**分组后** LazyColumn 条目数 ——
分组会把若干条折成一个过程组，条目数本来就该更少。

修法：改记 `entries = displayEntries.size`（与 `total` 同口径）。

### 3.4 屏上浮层被内容盖住

浮层放在 `ConnectedApp` 的 `BoxWithConstraints` **第一个子项**，
Compose 的绘制顺序就是声明顺序 → 后面所有内容都盖在它上面 → 主界面上看不见。

修法：提到 `DeepSeekHarnessApp` 最外层，包一个 Box，浮层作为**最后一个**子项。

### 3.5 诊断开关依赖被测功能可用

开关原本只在设置页，而设置页在**连接门闩之后** —— 连不上时进不去，
恰恰最需要日志的时候用不了。修法：连接页右上角加虫子快捷开关。

## 四、vivo 平台限制与绕行方案（实测）

### 4.1 输入法拒绝一切外部文本注入

| 手段 | 表现 |
|---|---|
| `input text '<464 字符>'` | 只进前 ~80 字符 |
| 分 12 段逐段输入 | 仍只进前几十字符 |
| `KEYCODE_PASTE`（279） | 无效 |
| 长按弹粘贴菜单 → `input tap` 点它 | 输入法浮层不响应注入点击 |
| `KEYCODE_DEL` ×60 | 删不动 |
| `service call clipboard 2 s16 '<text>'` | ✅ **写剪贴板成功**（唯一可用） |

### 4.2 文件选择器不索引 adb push 的文件

`documentsui` 的「文档」视图只列 MediaStore 认得的类型；
`adb push` 进 `/sdcard/Download/` 的 `.txt` 与 `.json` **都不出现**（实测）。
所以 SAF 那条路对 adb 部署不可用 —— 无人值守一律走**外部专属目录自动读取**。

### 4.3 顺带确认的两条

- `adb install -r` 在同签名覆盖时会**静默失败**（无输出、`lastUpdateTime` 不变），
  需要等系统弹确认页并手工点是 —— 脚本化装机必须检查时间戳而不是看退出码。
- 命令行超时后进程可能转后台（本次 `install` 跑到 300 s 转 job），
  别急着判失败，先看 `lastUpdateTime`。

## 五、怎么用

### 5.1 开日志

- 连接页：右上角**虫子图标**（实心=开，空心=关）
- 或 设置页 → 操作日志 → 记录窗口与会话操作

### 5.2 读日志（三种场合）

```bash
# ① 有电脑：直接读文件（推荐）
ADB=/media/wangke/OFFICE/workspace/android-toolchain/sdk/platform-tools/adb
"$ADB" shell "run-as io.github.westanke.dshcompanion cat files/diag.log"

# ② 有电脑但想实时跟
"$ADB" logcat -s DSH_DIAG        # vivo 上可能为空，见 §1.1

# ③ 没电脑：App 内 设置 → 读日志（整段进剪贴板）
```

### 5.3 无人值守连接（adb 部署）

```bash
ADB=.../platform-tools/adb
D=/sdcard/Android/data/io.github.westanke.dshcompanion/files
"$ADB" shell "mkdir -p $D"
"$ADB" push .diag/dsh-connection.txt $D/
# 启动 App → 配置文本自动填入输入框 → 点「导入并连接」
```

配置文本存在 `dsh-companion/.diag/dsh-connection.txt`（两个端点：局域网 + 虚拟网）。

## 六、怎么解读这些日志

| 看到 | 含义 |
|---|---|
| `ROUTE … → 原生/ChatDetail` + `COMPOSE ChatDetail 渲染` | 原生页确实在渲染；两条都缺 = 走的是别的路径 |
| `ROUTE … → WebView/ChatWebScreen` | 网页版在渲染（设置里开了「用网页版聊天页」） |
| `落底 effect 启动` 有、后面没有循环日志 | effect 跑了但循环立刻退出（列表空/已到底） |
| 连 `落底 effect 启动` 都没有 | effect 没执行 —— 查渲染路径，不是查滚动逻辑 |
| `落底循环退出：isScrollInProgress=true（用户拖动）` | 用户真的在拖（唯一合法置位依据） |
| `贴底跟随未触发：isAtBottom=false` | 用户在翻历史（正常）**或**判据失灵 |
| `（同前，已重复 N 次）` | 该行连续重复 N 次，只落了摘要（指数抑制） |
