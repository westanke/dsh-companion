## 二、核心发现：滚动位置被 history 重建冲掉

### 2.1 证据链（2026-10-18 14:47:18 → 14:47:26，同一会话）

```
14:47:18.523 #17 SCROLL 落底循环结束：scrollBy=0（物理底部），共 26 拍
14:47:25.969 #18 SCROLL 贴底跟随触发：isAtBottom=true entries=47 可见=39-47/48 first=39/-147
14:47:26.003 #19 SCROLL snapshotFlow collect 发射：totalItemsCount=1      ← ★ 列表被清空
14:47:26.301 #20 SCROLL snapshotFlow collect 发射：totalItemsCount=48
14:47:26.324 #21 SCROLL snapshotFlow collect 发射：totalItemsCount=1      ← ★ 又清空
14:47:26.725 #22 SCROLL snapshotFlow collect 发射：totalItemsCount=48
14:47:26.882 #23 SCROLL 贴底跟随未触发：isAtBottom=false 可见=0-8/48 first=0/0  ← ★ 位置归零
14:47:32.525 #24 SCROLL 贴底跟随未触发：isAtBottom=false 可见=0-8/49 first=0/0
14:47:43.830 #27 SCROLL 贴底跟随未触发：… 可见=0-9/50 first=0/0
```

`#18` 时视图在 `39-47/48`（底部，跟随正常触发）；
`#19/#21` 列表被瞬间清空（`totalItemsCount=1`，只剩「加载更早消息」那一项）；
`#23` 之后 `first=0/0` —— **视图被甩回顶部且再不回来**。

### 2.2 根因

1. **history 被周期性替换**：`totalItemsCount` 在 `48 → 1 → 48 → 1 → 48` 之间跳变，
   说明 `state.history` 被短暂置空/重建（流式刷新期间反复发生）。
2. **列表清空的那一瞬，LazyColumn 把滚动位置重置为 0**。这是 Compose 的正常行为：
   条目数归零后，先前的位置无处附着。
3. **内容回来后位置不恢复**，而 `落底循环` 只在 `LaunchedEffect(selected.id)` 里跑一次
   （进会话那一刻），对**后续**的重建无能为力。
4. 于是 `isAtBottom` 永久为 false，**贴底跟随被自己的守卫锁死**。

这同时解释了另两个现象：
- 用户最初反馈的「每次进入会话默认在当前页面顶段」——同一类问题；
- 此前观测到的 `53→1→53`、`43→53→43` 跳变——同一个重建。

### 2.3 与代码注释的矛盾（第二个缺陷）

`ui/chat/ChatDetail.kt:499` 写着：

> 持续贴底的守卫是 `!userScrolled`：用户一旦**主动滑过**（离底超过阈值）就停手，
> 不再打扰翻历史；没滑过就一直跟着新内容贴底 —— 这正是聊天产品的常规行为

但全仓 `grep userScrolled` **只在注释里命中，代码里不存在这个变量**。
实际守卫是瞬时的 `isAtBottom`（几何位置）。

| | 注释承诺（粘性意图） | 实际实现（瞬时几何） |
|---|---|---|
| 内容增长时 | 不受影响，继续贴底 | 立刻变 false → 拒绝跟随 |
| 位置被重建冲走 | 仍会自动追回 | 永久失效 |
| 用户翻历史后 | 需再次到底才恢复 | 到底即恢复 |

**注释描述的设计是对的，代码没实现它** —— 这正是「程序要求与实际行为不符」的具体形态。

## 三、相符性逐项明细

### A1 进会话落底 ✅

```
#7  SCROLL 落底 effect 启动：会话 …（totalItems=0）
#9  SCROLL 落底循环开始：等内容用 24 拍（totalItems=48）
#12 SCROLL 落底下推 5 拍  moved=600 first=12/-1224 total=48
#16 SCROLL 落底下推 25 拍 moved=271 first=39/-147  total=48
#17 SCROLL 落底循环结束：scrollBy=0（物理底部），共 26 拍
```
行为与约定一致：**每 32 ms 推 600 px，`scrollBy` 返回 0 即停**。
两次独立会话分别 18 / 26 / 29 拍到底，稳定。

### A2 流式贴底跟随 ❌

观测到 **200+ 条「未触发」**、`isAtBottom` 持续 false；有效「触发」仅在
`#18` 出现一次（位置尚未被冲走时）。详见 §2。

### A3 切会话 ✅

```
#33 ROUTE   路由判定 … selectedSessionId=null
#34 ROUTE   路由判定 … selectedSessionId=session-667ea09f-…
#35 COMPOSE ChatDetail 渲染：会话 session-667ea09f-…
#36 SCROLL  落底 effect 启动：会话 session-667ea09f-…（totalItems=0）
```
换会话后 `listState` 重建、落底循环重跑，与「`key(selected.id)`」的设计一致。

### A4 用户拖动 ⚠️

`isScrollInProgress` 退出分支（「落底循环退出：用户拖动」）**未出现**。
原因是落底循环在 1 秒内就结束了，之后用户再滑不会进入那段代码。
**结论：该分支实际上只在「进会话后 1 秒内恰好拖动」时才可能触发**，
不能作为「用户翻历史时是否被打扰」的常规判据 —— 要验那个得另加常驻观测。

## 五、建议的修法（未实施，待拍板）

**缺陷 1+2 是同一个修法** —— 把贴底守卫从「瞬时几何」改成「粘性意图」，
也就是注释里承诺的那个 `userScrolled`：

```
状态：var wantsBottom by remember(sessionId) { mutableStateOf(true) }

置真：用户滚到底（last visible index >= total - 3）
置假：用户主动上滑（isScrollInProgress 且离开底部）

贴底跟随：if (displayItems.isNotEmpty() && wantsBottom) scrollToItem(last)
落底循环：条件从「跑一轮」改成「只要 wantsBottom 就持续贴」
```

这样即使 history 重建把位置冲走，也会被自动追回 —— 治的是根因，不是症状。

**另外值得单独查的**：为什么 `state.history` 会被周期性置空
（`totalItemsCount` 掉到 1）。位置被冲走是**它的后果**；
即使守卫改好了，这种「列表闪一下」的抖动本身也该消除。
